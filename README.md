## Architecture

An external MCP client sends Streamable HTTP requests to `https://<gateway-host>/mcp` with `Authorization: Bearer <user-key>`. The gateway authenticates the user, lists tools from enabled upstreams concurrently, prefixes each tool as `<server>__<tool>`, and routes calls with a 10 second timeout. A failed upstream contributes no tools but leaves others working. Each call records the user, upstream, tool, duration, outcome, and request ID; external call responses also include `X-Request-ID`. The dashboard chat uses an OpenAI-compatible chat-completions endpoint and calls these same gateway functions as the logged-in user.

The WooCommerce MCP server talks to the WooCommerce REST API. It uses a WooCommerce consumer key and secret from Kubernetes Secrets. This is simpler and more portable than invoking WP-CLI for each tool call. The two other servers are `catalog` and `clock`; they demonstrate aggregation, though a richer second data source would make the cross-server demo more convincing.

## Local setup

Prerequisites: Node 24, Docker Desktop with Kubernetes or another Kubernetes cluster, Helm 3, and a maintained Ingress controller. The local chart uses `store.localhost` and `gateway.localhost`, which resolve to loopback without editing the hosts file on this Windows setup. Traefik was installed separately using its official Helm chart. A CNI that implements NetworkPolicy is required to enforce gateway-only upstream access; Docker Desktop's local network-policy behavior has not been verified.

Install Traefik for a fresh local cluster with `helm upgrade --install traefik traefik/traefik --repo https://traefik.github.io/charts -n traefik --create-namespace --wait`. On Docker Desktop, its LoadBalancer was reachable on localhost port 80. Verify both hosts with `curl.exe --noproxy "*" http://gateway.localhost/healthz` and `curl.exe --noproxy "*" http://store.localhost/`.

1. Run `npm ci` and `npm run build:web`.
2. Build images: `docker build -t urumi-gateway:local -f Dockerfile .` and `docker build -t urumi-upstream:local -f Dockerfile.upstream .`. Load images into Kind or k3d if needed. For this local deployment, the updated gateway, upstream, and frontend files are mounted via chart ConfigMaps because image rebuild access was unavailable to the agent. After `npm run build:web`, copy the files in `web/dist` into `helm/urumi/files/web` and copy `src/gateway.js`, `src/db.js`, and `src/chat-policy.js` into `helm/urumi/files` before upgrading. Production images should include the same source files; set `storePublicUrl` for the Store link.
3. Prepare a private Helm values file outside Git with `secrets.mariadbPassword`, `secrets.mariadbRootPassword`, `secrets.gatewayAdminPassword`, and optional `secrets.llmApiKey`. Set `llm.baseUrl` and `llm.model` for chat. Do not commit credentials. Store the WooCommerce REST consumer key and secret in a separate Kubernetes Secret named `urumi-woo-credentials` with keys `consumer-key` and `consumer-secret` in the `urumi` namespace. The local live cluster already has this Secret; do not copy it to Git or reveal it in a demo.
4. Before installing the chart, create namespace `urumi`, then create the image ConfigMap: `kubectl create namespace urumi` followed by `kubectl create configmap urumi-storefront-assets -n urumi --from-file=assets/storefront`. This includes the eight WebP assets and the small prompt-provenance Markdown file. Do not use client-side `kubectl apply` for this binary ConfigMap: its last-applied annotation can exceed Kubernetes' annotation limit. To update it, run `kubectl create configmap urumi-storefront-assets -n urumi --from-file=assets/storefront --dry-run=client -o yaml | kubectl apply --server-side --force-conflicts -f -`, then increment `storeAssetsVersion` in `helm/urumi/values.yaml` and upgrade Helm to roll WordPress.
5. Install: `helm upgrade --install urumi helm/urumi --namespace urumi --create-namespace -f helm/urumi/values-local.yaml -f my-secrets.yaml`.
6. Visit the storefront and finish WordPress installation. Install and activate WooCommerce from WordPress admin. Enable Cash on Delivery. Create a REST API key with read/write permissions and populate `urumi-woo-credentials`. The connector uses OAuth 1.0a HMAC-SHA256 for the local HTTP store and Basic auth only for HTTPS stores. It supports WordPress's query-style REST routing, so Apache permalink rewrites are not required.
   For the optional local merchandise demo, copy `assets/catalog/.` to `/tmp/urumi-product-images` in the WordPress pod, then copy `scripts/seed-demo-products.php` to `/tmp/seed-demo-products.php` and run `php /tmp/seed-demo-products.php` there. The script is idempotent: it creates 24 products by SKU (four original plus twenty new), imports a photo only when a product lacks one, categorizes the earlier mug and hoodie, and renames those two sample products without changing their IDs or orders. Imported photos persist in the WordPress uploads volume. It is not run automatically in production.
7. Visit the gateway URL and sign in as `admin` using `secrets.gatewayAdminPassword`. The three internal MCP services are registered automatically. Add a member in Team, then issue API keys from each account.
8. Configure an external MCP client with the gateway URL and a member's API key as a bearer token. Ask it to list products or orders. The chat form in the dashboard uses the configured LLM.

## VPS or k3s

Push both images to a registry. Set image names, real DNS names, and the k3s storage class in `values-prod.yaml` or a private override. Set up DNS and an Ingress controller, then run the same `helm upgrade --install` command with `values-prod.yaml`. Add TLS through your Ingress or cert-manager setup. Back up the MariaDB, WordPress, and gateway persistent volumes before upgrade. `helm history urumi -n urumi` and `helm rollback urumi <revision> -n urumi` handle chart rollback; database schema changes may need a separate restore plan.
